# Public-repository security review — 2026-10-04

## Changes in this round

* Password reset now requires a validated, operator-configured HTTPS `APP_URL` origin; it never builds the email link or template `{domain}` from a request header. Missing/invalid configuration disables reset for all addresses before account lookup. Set it to the real shop origin (no path, credentials, query or fragment). Invalid nonempty configuration makes general absolute links fall back to localhost rather than an attacker-controlled Host. If it is absent, non-sensitive legacy rendering still uses the request host for compatibility; enforce a Host allowlist at the edge even when configured.
* Recovery tokens use 32 random bytes encoded as hex, are saved before mail is sent, and are consumed with a conditional update that includes the original token, expiry and unbanned status; a zero-row update is refused. This closes the double-use window at that update, but has not been concurrency-tested against the vendor schema. A concurrent reset request may invalidate an earlier email. SMTP failure still yields the neutral response and the user must wait before requesting again.
* Known, unknown, throttled and DB-write-failure recovery requests have the same response text/status (timing is not equalised; this is not complete enumeration protection). OTP and 2FA redirect URLs are root-relative, so those tokens do not rely on Host. The legacy canonical HTML tag escapes the request URL.
* No real mail, production data, payment, licensing or supplier operation was performed. GachtheFast remains disabled/credit-locked.

## Evidence and limitations

On isolated native PHP 7.4 and 8.2: `canonical_origin_test.php` 20 checks and `auth_reset_endpoint_test.php` 7 checks per version, both zero failures. The second runs the real endpoint in subprocesses with fake DB/mail and checks the generated URL, request ordering, neutral responses and a simulated stale update; it is not an SMTP, database-engine or concurrent-request test. `auth_guard_test.php` 19 checks and `security_headers_test.php` 16 checks per version; these are mostly source-level. Full `bash tools/dev/run.sh`: lint 328/0, scanner 240/0, 38 preview pages, 64 suites with 8 NOT RUN and 0 failures. The isolated native auth test above ran separately; tests marked NOT RUN in the WASM gate must not be counted as passed. No production performance benchmark was run in this round.

A limited high-confidence pattern scan of 504 tracked non-public-asset text files in the working tree found no matching private-key headers or selected GitHub, AWS, Stripe live and Google API key formats. It excluded assets, large/binary files and vendored references and did **not** scan commit history, all credential formats, databases, logs or deployment systems. It is not evidence that the public repository is secret-free. Review public git history, releases, actions logs and deployment copies with a dedicated secret scanner; if any credential was ever published, revoke/rotate it at its issuer even if removed from Git. Do not paste secrets into issues or logs.

## Operator priorities before public deployment

1. Enforce HTTPS and an exact Host allowlist at the proxy/web server; verify `APP_URL`, trusted proxy settings, route rewrites, private file denies and uploads not executing scripts on the actual host. `.htaccess` is not a security policy for Nginx or a static server. Confirm reset with a test mailbox and production-equivalent staging, without recording the link.
2. The reseller API still uses URL keys and allows GET `create-order`; `api/importAccount.php` accepts a privileged key and inventory in request parameters, including GET. URL keys and stock contents may appear in access logs, browser history, monitoring and upstream services. Restrict network access at the edge, rotate potentially exposed keys, protect/redact logs and plan a coordinated POST/auth-header migration with API consumers. No breaking API change was made without such a plan. Review stock import ownership, duplicates and concurrent writes.
3. Reseller/web checkout is not end-to-end atomic across debit, inventory and suppliers; correlation is not a durable idempotency claim. Do not automatically retry uncertain purchases; reconcile with the support runbook. Verify real schema, transaction engines, unique constraints, backup and failure recovery before production.
4. Add independent security review, dependency and history scanning, protected deployment configuration, monitoring and rate limiting for authentication/recovery and APIs. Test supported PHP and real schema on staging; PHP 7.4 was used only for compatibility testing and is out of security support. Scanner zero findings is not a security certification.
